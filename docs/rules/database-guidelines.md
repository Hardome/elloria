# База данных и миграции

API использует PostgreSQL 18.6, Drizzle ORM и SQL-миграции.
Команды ниже выполняются из корня репозитория.

## Источники

- [src/db/schema/contacts.ts](../../api/src/db/schema/contacts.ts) — таблица заявок и `ContactRow`.
- [src/db/schema/index.ts](../../api/src/db/schema/index.ts) — экспорт таблиц.
- [src/db/migrations](../../api/src/db/migrations) — SQL, снимки и журнал миграций.
- [drizzle.config.ts](../../api/drizzle.config.ts) — настройка генератора.
- [plugins/database.ts](../../api/src/plugins/database.ts) — подключение БД как `app.db`.

Новые предметные таблицы размещайте рядом с `contacts` и экспортируйте через `index.ts`.
Для числовых ID используйте существующий подход:
`integer().primaryKey().generatedAlwaysAsIdentity()`. Тип записи выводите из таблицы.
Запросы приложения размещайте в репозиториях модулей.

## Изменение схемы

1. Обновите TypeScript-схему.
2. Сгенерируйте миграцию:

   ```sh
   pnpm --filter @elloria/api run db:generate
   ```

3. Прочитайте созданный SQL: проверьте переименования, удаления и сохранение данных.
   Не редактируйте снимки и журнал в `migrations/meta/` вручную.
4. Примените миграции к подготовленной локальной БД:

   ```sh
   pnpm run db:migrate
   ```

5. Обновите затронутые репозитории, преобразования и HTTP-контракт.
   Выполните `pnpm --filter @elloria/api run check`.

Генерация SQL не меняет БД. `db:migrate` применяет только новые миграции;
повторный запуск не должен изменять существующие данные.
При первом запуске достаточно применить имеющиеся миграции, генерировать начальную заново не нужно.
Начальная миграция рассчитана на пустую БД и не переносит прежние данные Knex.

Схему, SQL, снимок и журнал сохраняйте одним изменением.
Не редактируйте уже применённые миграции: изменения оформляйте новой миграцией.
Для просмотра есть `pnpm --filter @elloria/api run db:studio`; это не замена миграциям.

## Обратные изменения

В проекте нет команды отката `down`. Возврат прежней структуры оформляйте новой
миграцией после изменения схемы обратно и проверки SQL.
Удаление файла или записи из журнала БД не возвращает структуру назад.

Обратная миграция не восстанавливает удалённые данные.
До потенциальной потери данных определите способ их сохранения и восстановления.
Не применяйте экспериментальные миграции к рабочей БД.

## Тестовая БД

Vitest создаёт отдельную БД, применяет миграции и проверяет повторное применение,
затем удаляет временную БД. Пользователю подключения нужны права создавать и удалять БД.
Настройка использует `TEST_DATABASE_URL`, а при его отсутствии — `DATABASE_URL`.
Не используйте production-подключение для тестов.
Пример выделенного PostgreSQL — в [API README](../../api/README.md#проверки).
