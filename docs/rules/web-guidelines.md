# Разработка Web

Web использует Next.js App Router, React, TypeScript и Tailwind CSS.
Код организован по FSD, по образцу [Stageby](https://github.com/Hardome/stageby).
Маршруты Next.js отделены от слоёв приложения:

| Каталог | Назначение |
| --- | --- |
| `web/app/` | Точки входа Next.js: маршруты, metadata, sitemap и favicon |
| `web/src/app/` | Корневой layout, стили и шрифты |
| `web/src/pages/` | Страницы; секции и данные главной остаются внутри `home` |
| `web/src/widgets/` | Общие крупные блоки: шапка и подвал |
| `web/src/features/` | Сценарии: заявка на обратную связь и выбор дома |
| `web/src/entities/` | Повторно используемые предметные данные: компания |
| `web/src/shared/` | Независимые UI-компоненты, навигационные хуки и конфигурация |
| `web/public/` | Изображения и видео |

Каталог [web/pages](../../web/pages/README.md) не содержит маршрутов: он не даёт Next.js
использовать FSD-слой `src/pages/` как Pages Router. Сохраняйте его при переносах.

Слой импортирует только нижележащие слои: `app` → `pages` → `widgets` → `features` →
`entities` → `shared`. Соседние срезы одного слоя не импортируют друг друга.
Внутри среза используйте относительные импорты, снаружи — алиас `@/` и публичный `index.ts`.
Например, форма доступна через `@/features/contact-request`, а её внутренний `ui/`
не предназначен для внешних импортов. В `shared/ui` отдельный файл компонента служит
точкой входа; группы `icons`, `media-gallery` и `media-slider` имеют собственные `index.ts`.

Внутри среза раскладывайте код по назначению: `ui`, `model`, `lib`, `api`.
Файлы называйте в `kebab-case`, компоненты и типы — в `PascalCase`.
Не создавайте пустые слои и срезы ради структуры. Код одного экрана оставляйте в его странице;
в `widgets` и `entities` выносите блоки и предметные объекты при повторном использовании.

Границы и публичные API проверяет [Steiger](../../web/steiger.config.ts).
Как в Stageby, отключено только требование нескольких потребителей среза:
самостоятельный сценарий или страница могут иметь одну точку подключения.
Соблюдайте настройки Biome и ESLint. Форматирование и сортировку импортов выполняет
Biome; команды проверок описаны в [Web README](../../web/README.md#проверки).

## Маршруты и компоненты

Страницы и layout остаются серверными, пока им не нужны интерактивность, состояние
или браузерные API. Выделяйте такие части в клиентские компоненты с `'use client'`.
Не переносите серверную конфигурацию и секреты в клиентский код.
Для переходов используйте `next/link`, сохраняйте metadata и семантику заголовков.

Рабочий пример формы — [ContactDialog](../../web/src/features/contact-request/ui/contact-dialog.tsx).
Простые обработчики оставляйте рядом с разметкой; повторяемую или сложную логику
выносите по назначению. Не добавляйте библиотеку состояния или форм ради одного сценария.

## Запросы и формы

По умолчанию браузер отправляет `POST /api/contacts`, Next.js перенаправляет запрос в API.
Настройки адресов и момент их применения описаны в [конфигурации](../guides/api-configuration.md).
Не меняйте HTTP-формат только на стороне интерфейса: обновляйте контракт и сервер вместе.

Для формы сохраняйте подписи полей, маску телефона, согласие, состояния отправки,
успеха и ошибки. На время запроса блокируйте повторную отправку.
Проверка в браузере не заменяет серверную валидацию.
Проверяйте неуспешные HTTP-ответы, а не только сетевые исключения.

## UI и медиа

Используйте общие `Button`, `Input`, `Dialog` и компоненты типографики.
Оформление и доступность описаны в [правилах UI](design-system.md).
У изображений сохраняйте осмысленные подписи, у галерей — управление с клавиатуры.
Изменения проверяйте на узком и широком экране, включая длинный текст и прокрутку диалога.

## Проверки

Из корня репозитория выполните:

```sh
pnpm --filter @elloria/web run lint
pnpm --filter @elloria/web run typecheck
pnpm --filter @elloria/web run build
```

Проверьте изменённые сценарии по [ручному регрессу](../guides/regression.md).
Автоматического набора Web-тестов сейчас нет. При появлении сложной логики покрывайте
существенный пользовательский риск, не дублируйте реализацию тестами каждого компонента.
