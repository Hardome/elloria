# Разработка модулей API

Модули размещаются в `api/src/modules/<имя>/`. Рабочий пример —
[contacts](../../api/src/modules/contacts/index.ts).

## Границы модулей

| Файл | Ответственность |
| --- | --- |
| `index.ts` | Подключение маршрутов и создание репозитория с БД приложения |
| `routes.ts` | HTTP-пути, схемы, статусы и вызов предметных операций |
| `repository.ts` | Запросы к БД; без Fastify и HTTP-ошибок |
| `mapper.ts` | Преобразование записи БД в ответ, например `Date` в ISO UTC |
| `export.ts` | Формирование XLSX-выгрузки заявок |
| `contacts.test.ts` | Интеграционные проверки HTTP и реального PostgreSQL |

Создавайте только необходимые файлы. Сервис нужен при появлении бизнес-логики,
которой не место в HTTP-обработчике или запросе к БД.
Общая инфраструктура остаётся в `api/src/plugins/`, сборка приложения —
в [app.ts](../../api/src/app.ts).

Рукописные импорты используют `#app/*` и `#test/*` без расширения `.js`.
Типы записей выводите из схемы Drizzle, типы HTTP берите из генерации.
Не описывайте повторно поля контрактных типов.

## HTTP-контракт

Источник — [contracts/openapi.yaml](../../contracts/openapi.yaml).
Это редактируемый файл, а не собранный bundle. После изменения выполните
из корня репозитория:

```sh
pnpm run codegen
```

Генератор создаёт TypeScript-типы, Zod-схемы и типы Fastify в `api/src/generated/`.
Не редактируйте их вручную; сохраняйте результат вместе с исходным контрактом.
Клиент Web сейчас использует обычный `fetch`, генерируемого клиента нет.

Маршруты валидируют запросы сгенерированными схемами и согласуют ответы с контрактом.
Общие ошибки формирует [error-handler.ts](../../api/src/plugins/error-handler.ts):
`{ error, code, message, details? }`. Ошибки валидации содержат пути полей.
Не возвращайте SQL, внутренние ошибки и секреты в ответах.
Действующие endpoints и поведение заявок описаны в [API README](../../api/README.md#api).

## Порядок изменения

1. При изменении HTTP обновите OpenAPI и выполните `pnpm run codegen`.
2. При изменении хранения обновите схему и миграции по [правилам БД](database-guidelines.md).
3. Измените только затронутые слои. SQL оставляйте в репозитории, HTTP — в маршрутах.
4. Проверьте значимое поведение и ошибки через `app.inject` и реальный PostgreSQL.
   Ориентир — [contacts.test.ts](../../api/src/modules/contacts/contacts.test.ts).
   Закрывайте приложение после тестов и удаляйте только собственные записи по ID.
5. Из корня выполните `pnpm --filter @elloria/api run check`.
   При изменении контракта или поведения формы проверьте также Web.

Требования PostgreSQL и временной тестовой БД — в [API README](../../api/README.md#проверки).
Правила ключа выгрузки, логирования и доверенных прокси — в [конфигурации](../guides/api-configuration.md).
